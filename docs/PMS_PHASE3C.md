# Phase 3C — Safe in-house stay changes

Implemented for the reservation workspace. The next agreed phase is **3D — cashier shifts and reconciliation**. No production data conversion, deployment or feature enablement is part of this change.

## Workflows and authority

| Action | Operational authority | Financial authority and behavior |
| --- | --- | --- |
| Move room | `reservation.assign`; owner, manager, receptionist | Same category only; no financial entry and no financial figures disclosed to reception |
| Change room category | `reservation.category`; owner, manager | Explicit complimentary / charge / credit choice. `rates.manage` for agreed pricing; `billing.post` for a positive amount; `billing.adjust` for a credit |
| Extend stay | `reservation.extend`; owner, manager | Additional interval only at an active current-category rate, or an explicit negotiated final amount with `rates.manage`. Positive amount requires `billing.post` |
| Record early departure | `reservation.early_departure`; owner, manager | Explicit retain charge / exact agreed reduction choice. Reduction requires `billing.adjust`; no automatic unused-night calculation |

Fixed role permissions remain authoritative; membership documents cannot grant arbitrary permissions. Membership, owner/platform restrictions, PMS readiness and feature flags are rechecked transactionally. The legacy assignment endpoint rejects checked-in changes with `USE_STAY_CHANGE`.

Moves take effect only when their transaction commits. Their effective boundary is generated by the server in the successful transaction attempt, and the event's `createdAt` is a Firestore server commit timestamp. Clients cannot supply a move time. There are no scheduled or backdated moves. Early departure accepts `now` or an explicit future instant before current departure; the workspace resolves entered date/time in the saved hotel timezone, independently of the device timezone.

An extension never moves a guest automatically. Staff can move for the existing remaining interval, then separately review/confirm an extension. Both commands independently check capacity, maintenance, physical calendars and occupancy. A successful move does not promise an extension.

## Segment compatibility and inventory

`bookings.assignmentSegments` and `inventoryHolds.assignmentSegments` contain the same ordered exact assignment history. A segment includes stable ID, linked change ID, room and category identities/labels, effective start/end, inventory end including cleaning, and exact quarter-hour allocations. Moves add `closedByChangeId` to the closed segment. Current projections remain `roomType`, `physicalUnitId`, `physicalUnitLabel`, `physicalAllocations`, `endAt`, `inventoryEndAt`, `checkOut` and `departureTime`.

Unchanged bookings retain their existing single-category hold and physical allocation formats. Segments are initialized only by an authorized successful stay change. `originalStay` and `originalAllocationEvidence` retain the original operational/allocation evidence; quoted price, quote/provider snapshots and original rate-plan snapshots are preserved. An extension can record `operationalRatePlanId` without replacing the booked rate snapshot.

The evaluator requires a committed, single-unit hold, matching booking/hold/current physical allocations, contiguous canonical segments, and ownership of every saved physical slot. Missing or inconsistent records return reconciliation guidance. No repair, import, live migration or automatic reservation conversion occurs.

Inventory changes use counts before/after for each category/date/quarter-hour, writing only differences. Duplicate category slots across different room segments count separately. A move retains the old room's elapsed occupancy and turnover, including the rounded overlapping quarter-hour, while acquiring the destination occupancy and turnover. This additional capacity is validated explicitly. Unused future slots are released only if they belong to this booking. Unchanged physical slots and other bookings' slots are preserved.

Allocation readers, physical release, reservation release, setup verification and the read-only reconciliation report accept both formats. Maintenance already reads the same aggregate and physical calendars. Setup verification also verifies segment ownership in physical calendars. Room views, Today, search, cashier and customer details continue to read the current projections; issued documents retain their saved immutable details. Activity shows before/after room and departure, effective time, reason and authorized adjustment information. Folio entries retain stable change IDs and linked reduction sources.

## Pricing, commitments and documents

Overnight extensions price added hotel-local nights using existing date-price calculations and the applicable departure time. Hourly extensions price a supported additional whole-hour duration using arrival-date duration prices. The full resulting stay must satisfy midnight/operating-window restrictions. Public advance-booking, arrival-weekday and arrival-window requirements are not applied as if an in-house guest were arriving anew. Existing public booking callers retain their previous rules.

No new customer/platform fee is charged. Consumed accommodation is not repriced. Original booking totals are not overwritten: adjustments are immutable folio entries. Negotiated final amounts do not imply tax particulars. Calculated extension pricing is retained separately in the entry's details. Service durations, service prices, provider orders, collections and refunds are not enlarged or executed.

Early departure preserves elapsed history and the required turnover. Unresolved requests whose scheduled time/duration or stay/night pricing would be invalidated must first be resolved in Stay requests. Recording an earlier departure leaves the guest checked in. Checkout, excess-payment refunds and document issuance use their separate existing actions.

`prepareFolioPosting` is shared by the existing folio command and stay changes. It validates safe effective charges, open-entry accounting and documented-reduction guards before any write. Charges become additional invoice sources. Credits carry `reductionSourceId` and reduce the corresponding accommodation source for credit-note follow-up; existing original invoice line links are retained by the document workflow. Reversing a documented linked reduction is blocked with `DEBIT_NOTE_REQUIRED`. Issued invoices and credit notes are never modified automatically.

## Command contract and recovery

Private endpoint: `/api/partner/bookings/:bookingId/stay-change`.

- `GET`: authorized capabilities, current/original details, actual room history, eligible destinations with readable blockers, current-category rates and authorized accommodation reduction sources. Choices reserve nothing.
- `POST`: evaluate one proposed command and return before/after, effective/affected interval, permitted adjustment/balance/excess figures, document follow-up and a signed review token. Known blockers include human-readable resolution guidance.
- `PATCH`: confirm with `{ token, reason }` and `Idempotency-Key`. The token binds actor, hotel, booking, input and dependency fingerprint, with five-minute expiry.

Confirmation repeats authoritative reads inside one transaction: access/setup/policies, booking and hold, room/category status and occupancy, maintenance, calendars, pricing/date overrides, billing/payment/refund sources and invoice claims. Every read precedes writes. Inventory deltas, both segment copies, current projections, folio entries, housekeeping event, reservation event and request receipt commit together. Competing booking/lifecycle/payment writes conflict on booking reads, and competing invoices conflict on booking and claim reads. Lifecycle transitions now advance reservation/stay revisions too.

An exact-key replay returns the committed result after current operational authorization, even if the review has since expired or checkout has happened. Changed payloads conflict. The browser persists the original token, reason and key before sending, scoped by account/hotel/booking. A lost response freezes editing and keeps that exact request through reload and subsequent errors. Only a successful replay, or a known first-attempt rejection with no prior uncertainty, clears it. A stale review requires a fresh explicit review; background refresh does not replace drafts.

Successful commits invalidate hotel-scoped server Today generations after commit and trigger the existing browser operational invalidation. Room, housekeeping, workspace, financial and date-dependent Today queries refresh together. No hotel data is written by a preview.

## Supported limits and rollout

The existing limits remain: at most 30 hotel-local overnight nights (or a stricter rate maximum), at most 24 hourly hours (or a stricter rate maximum), and the allocator's 32-day maximum interval including turnover. Additional hourly duration must have a supported duration price. A stay supports at most 60 room segments; excess changes are explicitly blocked. Group/quantity holds, missing exact physical history and invalid historical/currency records require reconciliation, not conversion.

In-house stay changes are available by default to authorized hotel staff. `PARTNER_RESERVATIONS_STAY_CHANGES` is no longer read; missing or legacy `false` values do not disable the workflow. Existing allocation/PMS gates, role permissions and financial/inventory checks still apply. Release compatible application and worker artifacts and the existing source indexes together. New queries reuse existing property/status and booking-source indexes; no additional composite index is required by Phase 3C. Do not enable an older application or worker against changed records. No migration is required or supplied.
